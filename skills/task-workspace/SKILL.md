# 任务工作区约定（task-workspace）

处理任何多步骤任务时使用本技能。

## 何时使用

- 任务需要多轮对话、多个产出文件，或可能跨会话继续；
- 用户希望事后能只看一个文件就明白任务做到哪一步；
- 需要给任务留下可回滚的历史（git）。

一句话：**一个会话一个文件夹，开工先建目录，进度只写一个文件，任务过长就建仓库。**

## 硬性规则

1. **一个会话只用一个文件夹**
   同一个会话在工作区里最多只出现一个任务文件夹：`task_new` 会认领本会话的目录（目录内 `.dsh-session.json` 记录归属），第二次调用直接**复用**旧目录并返回 `reused: true`，不会新建第二个。这个会话的所有产出与改动都在该目录内完成。
   需要改到别的文件夹（改名、跨目录清理、修别的任务的文件）时，先把要动的清单和理由告诉用户，得到同意再动手。

2. **一个任务一个目录**
   开工第一步调用 `task_new`，得到 `<工作区根>/<任务名>-<YYYYMMDD>/`。
   任务目录直接放在工作区根目录下，不要建 `tasks/` 之类的中间层。

3. **一个任务一个进度文件**
   目录内唯一的进度文件是 `PROGRESS.md`（六段：目标 / 状态 / 当前进度 / 下一步 / 产出物 / 变更日志）。
   每次有实质进展就调用 `task_progress` **整体覆盖更新**它，并把当次改动追加进「变更日志」。
   不要另建 `notes.md`、`todo.md`、`plan.md` 之类平行文件——需要新板块就扩 `PROGRESS.md`。
   「当前进度」写得长也没关系：超过约 18 行会自动压缩成摘要，原文进 `<details>` 折叠区。

4. **任务过长就建 git 仓库**
   满足任一条件就在该任务目录内建仓库（`task_git`）：
   - 预计超过 3 轮对话；
   - 需要跨会话继续；
   - 预计产出文件超过 10 个；
   - 用户明确要求。

   首次 commit 用 `chore: 初始化任务仓库`，之后用 `progress: 更新进度文件` 或更有信息量的消息。

5. **收尾回填**
   任务结束时把结论写进「当前进度」与「产出物」（含路径），状态改为「已完成」。

## 工具

| 工具 | 用途 |
| --- | --- |
| `task_new` | 建目录 + `PROGRESS.md`，可选 `init_git: true` 顺手建仓库；本会话已有目录时直接复用（`reused: true`） |
| `task_progress` | 覆盖更新进度文件（`summary` / `changelog` / `status` / `next` / `deliverables` / `goal`） |
| `task_git` | 初始化或提交任务自己的仓库 |
| `task_list` | 列出当前工作区已有的任务目录 |
| `task_tidy` | 整理工作区：分类顶层条目、重写索引、清掉垃圾/缓存/越界任务目录（空目录只提示不删）（默认 dry run，`apply: true` 才删） |

`task_progress` 与 `task_git` 都可以用 `task_dir`（目录）或 `task`（任务名片段）定位任务。

## 无模型时（命令行）

```bash
dsh-task new "<任务名>" "<目标>" --git [--session <会话id>]
dsh-task progress "<任务目录|任务名>" --summary "做到哪了" --changelog "这次改了什么"
dsh-task tidy [--apply] [--empty-dirs]           # 先看清单，确认后加 --apply 清理
dsh-task git "<任务目录|任务名>" --message "chore: 初始化任务仓库"
dsh-task list
dsh-task config --root "<工作区根>"
```

## 常见错误

- 同一个会话建出两个以上任务文件夹 —— 违反「一个会话一个文件夹」（`task_new` 已自动复用）；
- 改到别的任务的目录却不先问用户 —— 越界改动；
- 把进度写进聊天记录而不是 `PROGRESS.md` —— 会话结束后就丢了；
- 每个小步骤都建新文件 —— 违反「唯一进度文件」；
- 忘记写「变更日志」—— 失去可追溯性；
- 长任务不建 git —— 无法回滚、无法对比。
